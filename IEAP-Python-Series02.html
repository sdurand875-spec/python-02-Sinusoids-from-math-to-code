1. Create and improve a notebook to plot sinusoidal signals¶

The goal of this series is to start coding something useful, from theory to code.
The preliminary step was a homework to make clear the theory and concepts relative to sine waves and their properties.
The current step is to code the generation of a sine wave and its visualization, while ensuring the code is clean and well-documented, and also keeping track of the changes made during the process.

As usual, we will use a new Git repository for this new problem, with a Jupyter Notebook in which we combine theory and math (in Markdown cells) and implementation (in code cells). The goal is to have a notebook that is easy to read, easy to understand, easy to modify, and easy to reuse.

NOTE: Your ultimate goal is to create a notebook that generates and plots sine waves, which can be done in a matter of minutes using AI. But this ultimate goal is just a pretext for discovering what Copilot cannot do for you: think and improve your code iteratively, while keeping all versions of your code using GitHub.

2. Reproducibility of research and quality of code¶

Reproducibility of research is the ability to reproduce the results of a study using the same data and methods as the original study. It is a fundamental principle of scientific research, which depends on the quality of the code used to analyze the data. Hence, the quality of researcher's code is a very important topic in data analysis for scientific research (as it is in software engineering).

This is very well explained in The Turing Way. Take a look at the chapter about Code Quality (in the section about reproducible research).

Paraphrased from https://www.codegrip.tech/productivity/what-is-code-quality-why-is-it-important/

Code quality measures of how well can code communicate between researchers. Similar analyses may have an evident difference in code from researchers to researchers, but what matters most is that the quality of code remains the same throughout. A quality code is one that is clear, simple, well tested, bug-free, refactored, documented, and performant. But the primary measure of high-quality code in compliance with the specification depends on the needs of the research.

3.4. Ask a colleague for a code review before merging your final branch into the main branch¶

Once you are satisfied with your final version, ask a colleague to review your code. You will learn a lot from this experience, and your colleague will learn a lot too.

The why of code review is very well explained in The Turing Way. Take a look at the chapter about Code Review (in the section about reproducible research).

How to do it? Here are some tips:

  1. Add your colleague as a collaborator to your GitHub repository (if you have not done it yet).
  2. Create a pull request (PR) for your changes, including a description of what you have done and what you would like feedback on.
  3. In the PR page on GitHub, click on "Request a review" from your colleague.
  4. Be open to feedback and ready to make changes based on the review.
